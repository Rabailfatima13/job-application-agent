# Reflection — Working With AI on the Job Application Agent

*What the AI assistant did well, where it fell short, and what I'd do differently — written honestly, against the actual history of this project, not a generic list.*

## What AI did well

**Catching real bugs through structured, independent audits.** The most valuable AI-assisted work in this project wasn't the first pass of writing code — it was the repeated audit passes near the end. Three separate, independently-run audits of the same finished codebase found four genuine, narrow bugs that had been sitting there, passing every existing test: a search failure mode that would have crashed the whole pipeline instead of degrading gracefully, a misleading error message that pointed at the wrong environment variable, an unenforced consistency rule between two fields on the same model, and dead configuration for a feature that was never actually built. None of these were found by "does it work" checks — they were found by someone (in this case, an AI collaborator) deliberately trying to break each component's assumptions.

**Never trading test coverage for speed.** Across every finalization pass, the AI consistently ran the real test suite before claiming anything was fixed, and treated a broken test as something to *fix the cause of*, not delete or weaken. When it restyled the Streamlit results page, it read the entire 52-test UI test file first, specifically to find the exact strings and element types the tests depended on, rather than restyling first and seeing what broke. That discipline is why "434 tests passing, 98% coverage" stayed true through several rounds of real change, not just at the very end.

**Respecting explicit scope boundaries.** This project moved in narrow, single-purpose steps — "implement ONLY the parsing layer," "UI-only, backend frozen," "documentation-only, no code changes" — and the AI mostly held to whatever boundary was given in the moment, including refusing to silently build things (Docker, a multi-model comparison view, caching) that an earlier instruction had explicitly frozen, even when a later request implied they were now wanted.

**Being honest about what it couldn't verify.** More than once, the AI declined to state something as fact because it couldn't actually confirm it against the real code or a real run — excluding an unverifiable "38% fit" statistic from the mentor documentation rather than repeating it, and refusing to claim a known scoring edge case had been "fixed and confirmed" when it had only been fixed at the prompt level and never re-tested against a live model call.

## Where it fell short

**The same audits that found real bugs also proved those bugs existed for a while first.** The `met`/`match_level` inconsistency, the dead LangSmith config, and the JSON-crash bug weren't introduced and caught in the same breath — they shipped in earlier AI-assisted passes and sat there until a dedicated, later audit went looking. Fast, feature-focused AI assistance is good at making things *work*; it took a slower, adversarial pass — reading tests before trusting them, deliberately hunting for the failure case nobody wrote a test for — to make things *correct*.

**The prompt log fell behind.** `Prompts.md` is supposed to be a running record of every AI interaction on this project, but it stopped being updated verbatim partway through Week 7 — several real sessions (the grounding fixes, multi-provider support, the MCP server, the entire Streamlit UI) happened and were never logged in the moment. They could only be reconstructed afterward from commit messages, which meant the *what* survived but the *why*, and the exact original ask, didn't. Keeping a log current is a discipline an AI assistant can help with, but it doesn't happen automatically just because the assistant is capable of writing it — someone has to ask.

**A generic curriculum checklist and this project's own "finalization" instructions eventually collided, and that collision wasn't visible until late.** Several sessions in a row explicitly told the AI to treat the backend as frozen and to leave the multi-model comparison view, deployment, and caching as documented future work. When a later request asked to "fulfill every requirement" from a program-wide roadmap that specifically wanted those same three things, the tension had to be surfaced rather than resolved by guessing in either direction. That's the right outcome, but it would have been better to notice the roadmap's exact expectations earlier, rather than building a polished "finalization" story and then discovering it doesn't map cleanly onto the program's own checklist.

**Some things simply can't be delegated.** A live 20-minute presentation, a genuinely recorded demo video, and an actual deployed, publicly-reachable instance of the app all require a human's time, voice, and (for deployment) hosting credentials the AI doesn't have. It's easy to lose sight of that after a long stretch where nearly everything else on a checklist turned out to be automatable.

## Lessons I'm taking from this

1. **Small, explicitly-scoped prompts beat big ones.** "Implement ONLY X, do not implement Y, then stop" produced a codebase clean enough that a late audit could actually reason about it component by component. A single sprawling "build the whole thing" prompt would not have been auditable the same way.
2. **"Feature-complete" and "correct" are different claims, and only one of them is checked by running the demo.** The bugs that got caught late were all in code that already *worked* in the sense of passing every test that existed at the time. A real audit pass — not just a feature checklist — is what found the edge cases.
3. **Log as you go, not after the fact.** Reconstructing a development history from commit messages is possible, but it loses the actual reasoning and the exact original ask. A prompt log is only as useful as how current it stays.
4. **When a checklist and a standing instruction disagree, say so — don't quietly pick one.** Silently building the "frozen" features would have broken a real prior agreement; silently refusing the checklist would have left me thinking requirements were met that weren't.
5. **A large test suite is what makes speed *and* safety possible at the same time.** Every fast, confident final pass in this project — the audit, the UI redesign, the documentation rewrite — was only fast because 400+ existing tests could immediately prove nothing broke. Without that suite, the same work would have needed to be far more cautious and far slower.
